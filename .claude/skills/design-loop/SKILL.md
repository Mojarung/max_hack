# Цикл «посмотреть → оценить → исправить → проверить»

Область: $ARGUMENTS (если пусто - всё приложение).

Правила дизайна и параметры мок-режима - в `frontend/DESIGN.md`. Прочитай его до первой правки.

## 1. Подготовка

- `preview_start` с именем `frontend-mock` (порт 5174). Живой бэкенд не используй.
- Убедись, что главная открывается: `http://localhost:5174/?reset=1`.

## 2. Базовая оценка (параллельно)

Запусти в одном сообщении двух субагентов, каждому передай область и попроси работать в своей вкладке:

- `ui-critic` - экраны области: оценки по рубрике, находки P0-P2, сводка `__ui.audit()`.
- `ui-walkthrough` - сценарии, которые затрагивают область (по умолчанию все 7 из его описания).

Если агентов с этими именами нет в сессии (например, сессия открыта не в корне репозитория),
запусти `general-purpose` с инструкцией «прочитай `.claude/agents/ui-critic.md` и выполни его как свою роль».

Пока агенты работают, сам посмотри экраны области: скриншот в мобильном размере, светлая и тёмная тема.

## 3. План

Сведи находки в один список: убери дубли, отбрось противоречащие DESIGN.md (например, «добавить
красный»), отбрось то, что требует бэкенда. Отсортируй: P0, затем P1, затем P2 с высокой отдачей и низкой ценой.
Если находка спорная, выбери вариант, который ближе к принципам DESIGN.md, и зафиксируй причину.

## 4. Исправления

- Правь по одному смысловому блоку. Переиспользуй существующие компоненты (`StatusChip`, `VoteProgress`,
  `EmptyState`, `.card-soft`, `.sticky-cta`) и токены темы.
- Если меняется общее правило (новый паттерн, новый компонент) - обнови DESIGN.md в том же изменении.
- Новые данные, нужные экрану, добавь в мок (`src/mock/fixtures.ts`, `src/mock/server.ts`) только в
  рамках существующего API (`src/api/types.ts`).

## 5. Проверка после каждого блока

1. `cd frontend && npm run typecheck && npm run lint`.
2. Скриншоты изменённых экранов (мобильный размер, светлая + тёмная), при необходимости сценарии
   `empty`, `long`, `overdue`, `alert`, `error`.
3. `await __ui.audit()` - новых нарушений нет.

## 6. Повторная оценка

Снова вызови `ui-critic` только на изменённых экранах (и `ui-walkthrough` на затронутых сценариях).
Повторяй шаги 3-6, пока итог критика по каждому экрану не станет ≥ 8 и в walkthrough не останется P0,
но **не больше 3 итераций** - дальше отдача падает, остаток перечисли в отчёте.

## 7. Финал

- `npm test` и `npm run build`.
- Отчёт: таблица «экран - оценка до - оценка после», что изменено (с файлами), что осталось и почему.
